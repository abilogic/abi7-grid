# ABI7 Grid — аудит производительности

Версия кода: коммит `bcc3a82` (ABI7 Grid 1.0.0). Проверено: `src/abi7-grid.js` (2755 строк), `src/abi7-grid.css`, 7 плагинов.
Публичный API и поведение не менялись. Все 164 существующих теста проходят, добавлено 46 новых, итого 210/210.

## 1. Резюме

Ядро написано аккуратно: типизированные массивы для геометрии, пространственный индекс, DOM-пул, частичный пересчёт
раскладки, всё в одном `requestAnimationFrame`. Крупных алгоритмических проблем на горячем пути скролла нет.
Найдено **11 проблем**: 10 исправлены в коде, одна (композитные слои, №11) оставлена на ваше решение. Отдельно в §4 описана рекомендация про `pointermove`.
Самые заметные находки касаются не скролла, а **изменения данных** (`insert` / `remove`) и **накладных расходов на каждый кадр**.

## 2. Что и как исправлено

### 2.1. `DataStore.insert` и `remove` (проблемы 1, 2)
* **Было:** `records = records.slice(0, at).concat(list, records.slice(at))`, то же для `ids`. Каждый вызов копирует n элементов.
  `remove` проходит по всем n, собирает новые массивы и строит новую `Map` с нуля.
* **Стало:** вставка в конец делает `push`. Вставка в середину делает `splice` (для списков больше 10 000 элементов остаётся прежний путь, чтобы не упереться в лимит аргументов).
  Для `remove` позиция первого удаляемого находится через `Map id→index`. Дальше массивы уплотняются **на месте, начиная с этой позиции**.
  `Map` обновляется только для сдвинутых элементов. Порядок `removed` (по возрастанию индекса) и все события сохранены.

### 2.2. Инкрементальный пространственный индекс (проблема 3)
* `GeometryStore.set()` теперь записывает только реально изменившиеся прямоугольники и запоминает минимальный изменённый слот (`_dirty`).
  Раскладки (Masonry с чекпоинтами, Justified с пересчётом строки) пересчитывают несколько элементов до `from`, и многие из них получают прежние координаты.
* `buildIndex()` использует инвариант «списки в корзинах отсортированы по возрастанию номера слота».
  Из каждой корзины отрезается хвост `>= from`, затем добавляются только изменённые слоты: O(корзины + изменённые) вместо O(все элементы).
* **Безопасный откат на полную перестройку**, когда структура корзин могла измениться: сменилась ось, число корзин уменьшилось, или какой-то прямоугольник «прижат» к последней корзине (`_idxOverflow`).
  Последний случай возможен только у кастомной раскладки, которая возвращает высоту меньше своих элементов.

### 2.3. Принудительный reflow в каждом кадре (проблема 4)
`updateViewport` читает позицию скролла в `viewMetrics()` **до** `renderer.sync()`, а потом читал `root.scrollTop` ещё раз **после** того, как `sync` смонтировал, размонтировал и переместил карточки.
Чтение геометрии после записи стилей заставляет браузер выполнить layout синхронно, прямо внутри rAF-кадра, и это происходило в каждом кадре с изменениями DOM.
Теперь значения берутся из уже прочитанных `m.sMain` / `m.sCross`. Содержимое события `scroll` не изменилось (проверено для вертикальной и горизонтальной осей).

### 2.4. Остальное
* `onScroll`: одно событие, одна метка времени `_lastScrollAt`, **один** таймер, который перезапускается на остаток, если за время ожидания был ещё скролл. `scroll:stop` срабатывает через те же 140 мс тишины.
* `sync()`: штампы поколений на записях вместо `Set` и `[...keys()]`. `Map` обходится только если там есть то, что надо убрать.
* `matchMedia`: один живой `MediaQueryList` на окно. Если подменить `window.matchMedia`, объект создаётся заново.
* Прочие мелочи: одна `fixed`-структура на проход, бинарный поиск для pinned, буфер для `visible()`, ранний выход в `emit()`, одно чтение `getBoundingClientRect()` на `pointermove` при drag.
* `selection`: `select` и `deselect` применяют дельту из одного id, события и порядок `selected` те же.
* `reveal`: одна пара кадров на **пачку** смонтированных карточек. Карточки, смонтированные позже, образуют новую пачку и получают собственные два кадра, поэтому «скрытое состояние» по-прежнему успевает отрисоваться.

## 3. Измерения

Окружение: Node v20.20.2, 2 vCPU Intel Xeon @ 2.6 GHz, jsdom. Значения — медиана 5 запусков (`bench/compare.mjs`).

> **Ограничение методики.** jsdom не умеет layout и paint. Бенчмарк измеряет **JS-стоимость** библиотеки (данные, раскладка, индекс, виртуализация, учёт).
> Выигрыш от пунктов 4 и 11 проявляется только в реальном браузере. Для пункта 4 есть детерминированный тест, который доказывает, что принудительных чтений больше нет.

| Сценарий | До | После | Результат |
|---|---:|---:|---:|
| 1000 одиночных `insert()` в конец, 50k записей | 1123 мс | 12,5 мс | **90× быстрее** |
| Удаление 1 карточки около конца, сетка 100k (remove + layout + индекс) | 23,6 мс | 1,04 мс | **23× быстрее** |
| Добавление 50 карточек в сетку 100k (insert + layout + индекс + рендер) | 6,41 мс | 1,10 мс | **5,8× быстрее** |
| Добавление 1 карточки в сетку 30k | 1,80 мс | 0,65 мс | **2,8× быстрее** |
| `selection`: select + deselect одной карточки при 40k выделенных | 14,2 мс | 0,46 мс | **31× быстрее** |
| `reveal`: rAF-регистраций на 200 кадров быстрого скролла | 8132 | 202 | **40× меньше** |
| Таймеров на 1000 scroll-кадров | 1000 | 0,33 | **≈3000× меньше** |
| Вызовов `matchMedia` на 100 анимированных вставок | 100 | 1 | **100× меньше** |
| Чтений `scrollTop` на кадр скролла (из них после записи в DOM) | 2 (1) | 1 (0) | принудительный reflow убран |
| Первая раскладка 100k (Masonry) | 33,2 мс | 30,8 мс | без изменений |
| Полный relayout 100k: masonry / grid / justified | 11,0 / 5,8 / 12,3 мс | 11,0 / 5,5 / 12,4 мс | без изменений |
| JS-стоимость одного scroll-кадра в jsdom (4 сценария) | 56 / 71 / 133 / 156 мкс | 51 / 64 / 143 / 157 мкс | в пределах шума |

**Что не улучшилось и почему.** Полная раскладка и первая отрисовка не менялись: они уже линейные и быстрые (≈0,1 мкс на элемент).
Профиль scroll-кадра показал, что собственный JS библиотеки занимает единицы микросекунд: `sync` ≈ 8 мкс и `query` ≈ 5 мкс на кадр.
Остальное — jsdom и GC. Поэтому «ускорения скролла в микросекундах» заявлять нельзя. Исправления 4–6 убирают **структурные** издержки: принудительный reflow, лишние таймеры и аллокации.
В браузере они дают более стабильные кадры, но это нужно подтвердить в DevTools Performance (см. §6).
Сценарий «H» (200 pinned при выключенной виртуализации) тоже без изменений: в нём доминирует монтирование 8000 карточек. Бинарный поиск улучшает асимптотику, но на практике незаметен.

## 4. Не исправлено, но стоит решить

1. **Композитные слои на каждую карточку (проблема 11).** `.abi7-item { will-change: transform }` и `transform: translate3d(x,y,0)` вынуждают браузер выделять слой на каждую смонтированную карточку (сотни при большом `overscan`).
   Это память GPU и работа композитора, особенно на мобильных. Поскольку `translate3d` и `will-change` **описаны в документации как контракт** (`docs/pages/concepts.md`, `internals.md`), а эффект зависит от браузера и железа, я не менял их вслепую.
   Рекомендация: заменить на 2D `translate(x,y)`, а `will-change: transform` оставить только на `.abi7-animating .abi7-item` и `.abi7-dragging`. Затем сравнить в Chrome DevTools: Layers, Performance, GPU memory.
2. **`pointermove` при drag не склеивается по кадрам** (приоритет низкий). `_update()` (hit-test, `drag:move`, возможный `move()`) вызывается на каждое событие.
   Современные браузеры (Chrome) обычно сами выравнивают `pointermove` по кадру, поэтому реальный выигрыш зависит от браузера. Я его не измерял.
   Если понадобится: обрабатывать последнюю позицию раз в rAF-тике. Это меняет момент `drag:move` относительно события, а существующие тесты и документация ожидают синхронности.
   В этом проходе исправлено только удвоенное чтение `getBoundingClientRect()` (п. 8 таблицы).
3. Мелкие наблюдения без исправления: `selection` отдаёт в событии копию `selected` (O(selected) на событие, это часть формата события); `toggleClass` хранит `Set` на каждый id (память при `selectAll()` на сотнях тысяч);
   `_applyLoaded` перепривязывает смонтированные карточки, которые следом будут размонтированы.

## 5. Как проверялись исправления

* **Все 164 существующих теста проходят** (и на `src`, и на минифицированной сборке). `npm run validate` (сборка, `tools/check.js`, тесты): 210/210.
* **`tests/perf.test.js` — 46 проверок** (23 × `src` и `min`):
  * *Поведение не изменилось* (рандомизированные тесты с фиксированным сидом; `FUZZ_SEED=n` даёт другие прогоны):
    модель на обычном массиве для insert/remove/move; запросы окна и hit-test против перебора для 4 раскладок после случайных правок
    (append, вставка, удаление, update размеров, move, resize, смена gap, усечение 60% данных); кастомная раскладка с переполнением размера;
    события `scroll`, `scroll:stop`, `item:visible/hidden`, pinned, drag, selection, reveal.
  * *Дорогая операция действительно исчезла*: счётчики `setTimeout`, чтений `scrollTop` **после** записи в DOM, `matchMedia`, `getBoundingClientRect`, `requestAnimationFrame`.
* **Тесты проверены на обоих кодах.** Против **оригинального** кода все тесты поведения проходят (поведение идентично), а 5 тестов на производительность падают по ожидаемым причинам:
  `400 таймеров на 400 событий`, `40 чтений scrollTop после записи на 40 кадров`, `20 вызовов matchMedia`, `2 !== 1 чтений rect на pointermove`, `15 rAF на 14 карточек`.
* **Мутационная проверка.** Если сломать инкрементальный индекс (убрать `_dirty` или защиту от переполнения), тесты индекса падают.
  Первая версия теста на переполнение эту ошибку не ловила (число корзин не менялось). Тест усилен, теперь ловит.
* **25 дополнительных сидов** (`FUZZ_SEED=1..25`) × 14 тестов: без падений.

## 6. Как перепроверить в браузере

1. DevTools → Performance, запись при быстром скролле 20–100k карточек. Раньше в кадрах была фиолетовая полоса «Layout» с пометкой *Forced reflow* внутри `updateViewport`; теперь её быть не должно.
2. Timers: количество `setTimeout` при скролле должно быть ≈ 1 на жест.
3. `layout:end.duration` при `insert()` в большую сетку (в событии есть поле `duration`).
4. Для пункта 11: DevTools → Layers: число слоёв и память.
